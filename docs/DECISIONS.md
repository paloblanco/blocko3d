# BLOCKO3D design decisions

Every design decision agreed with the owner (Rocco), with the reasons, moved here unchanged from `docs/ENGINE.md` on 2026-11-11 so that file stays short. **Before changing a feature, read its part here** (search for the function or feature name): most behaviours were chosen on purpose, one at a time, and "asked for by the owner" or "agreed with the owner" means don't change it without asking. Add new decisions here, under the feature they belong to.

**`map(m, backs)`** (the owner's request and design): `backs` true sets that draw's material to `THREE.DoubleSide` (set on every draw, so a pooled object never keeps it), so through `palt` holes the far faces' insides show. The back face carries the front's face direction for outlines, which looks right in tests (outlines on and off at 2×). Default `FrontSide`, unchanged output.

**Drawing tiers** mirror PICO-8:

1. `map`: voxel maps, the equivalent of PICO-8's map.
2. `vox`: 8×8×8 voxel models for characters and items, the `spr` equivalent (see **Vox models** below).
3. Primitives: `cube`, `sphere`, `line3`.

Drawing is **immediate-mode**: `_draw()` re-submits everything every frame, with no scene graph.

**Maps**

- A map is a 3D array of tile indices; `0` is empty. There can be many maps, numbered 0, 1, 2… in cart order, plus any made with `map_new`.
- Each map has its own transform, so you can have dynamic geometry (a moving platform, a drawbridge) without models:
  - **origin**: a pivot point in the map's own block coordinates, non-integer allowed. Defaults to `[0,0,0]`. It is set when the map is declared and can be changed during play.
  - **pos**: where the origin sits in the world.
  - **angle**: `[pitch, yaw, roll]`.
- World point = `pos + R · (local − origin)`.
- **`map_set_origin` keeps the map in place on screen.** It quietly adjusts `pos` so only the pivot moves. The owner chose this explicitly.
- The transform lives on the map, not in the draw call. That way collision (`mgetw`) and drawing always agree.
- Queries:
  - `mget`/`mset` use grid coordinates.
  - `mgetw(m, x, y, z)` takes a world point and returns `[t, xi, yi, zi]`. It works for any rotation.
  - `mgetw(m, x, y, z, r)` is a sphere query. It returns the deepest hit, `[t, xi, yi, zi, nx, ny, nz, d]`, with a world-space push-out direction and depth, so collision is one line. `t` is 0 when nothing is hit.
  - `msetw` sets a block at a world point.
  - `mtow(m, x, y, z)` / `wtom(m, x, y, z)` (agreed with the owner): a point in the map's own grid to world space and back, as `[x, y, z]`, unrounded, from the map's current `_m` / `_inv` (the same transform `map()` and `mgetw` use, so they always agree). `wtom` floored equals `mgetw`'s cell. Uses: anything attached to a turned map (Tilt Maze's flag and start, Scrambler's arm ends, cars, riders and ride camera), and riding a moving platform (keep the rider's position in the platform's grid with `wtom`, move the platform, bring it back with `mtow`).
  - `mray(m, ox, oy, oz, dx, dy, dz, maxd = 100)` (agreed with the owner) returns the first solid block along a ray, `[t, xi, yi, zi, nx, ny, nz, d]`, same shape as the sphere query; all zeros on a miss. **n is the face hit as a grid direction** (the owner's choice, so `mset(m, xi+nx, yi+ny, zi+nz, t)` places a block on it; on rotated maps it differs from a world direction). d is in world units (map transforms only rotate and move). `rayQuery` in `js/engine.js` moves the ray into map space, clips it to the map's box and steps cell by cell (Amanatides & Woo). A ray starting inside a solid block hits it at d = 0 with n = 0. The direction needn't be normalized.

**Angles and axes**

- Angles are in **turns**: 1 is a full rotation, as in PICO-8.
- Rotation order is **yaw, then pitch, then roll**. In Three.js this is Euler `'YXZ'`, built with x = −pitch.
- y is up and one block is one world unit.
- +z is "forward":
  - Positive pitch tips +z up toward +y.
  - Positive yaw turns +z toward +x.
  - Positive roll turns +x toward +y.

**Tiles**

- Up to 255 tiles, numbered 1–255 (raised from 63 by the owner: a map block is one byte, so 255 is the most; the atlas is 24×2048, WebGL2's guaranteed minimum texture size).
- Each tile has three 8×8 textures: **top, sides, bottom**, like Minecraft but simpler.
- Pixels store **palette indices**, never colors.

**Rendering**

- **No shading or lighting, and no options for it.** Every face shows its texture exactly as drawn.
- The background is one palette color, set with `bg(c)`.
- The screen is **square (1:1)** and renders at 256×256, scaled up with crisp pixels.

**Camera**

- Set with `cam_set_pos`, `cam_set_lookat`, and `cam_set_fov`.
- FOV is in turns, with a **default of 0.25** (90°), and applies to **the longer side of the view** (agreed with the owner, for clip views: left/right halves get 90° up-down, top/bottom halves 90° across; on the full square screen both are 90°). `aimCamera` turns it into three's vertical fov.

**`clip(x0, y0, x1, y1)`** (agreed with the owner: corners like `rect`, also clips `print`/`rect`/`rectfill`): draw only inside a rectangle; `clip()` resets. Persistent draw state like `pal`; `reset()` clears it. **Each `clip()` starts a new view** (`startView`/`endView` in `js/engine.js`): every 3D draw records the current view (`o.userData.view`), and a view takes its camera, fov and bg **as they are when it ends** (the next `clip()` or the end of `_draw`), not when it starts, so games that set the camera after drawing still work, and a cart with no `clip()` is one full-screen view rendered exactly as before (checked pixel-identical at 1× and 3×). Views with no 3D draws are skipped (so a clip around HUD text never paints over anything). `endDraw` clears the canvas to bg when there's more than one view or a partial one, then for each view in order: show only its objects, aim the camera (aspect from the rectangle, fov on the longer side), set the viewport and scissor on the scene target (`rt.viewport/scissor/scissorTest`, three takes them from the target) and clear it to the view's bg, render, then run the outline pass(es) into the same rectangle of the canvas (and masks at 2×/3×). The outline and grow shaders get `uRect` and clamp every neighbor lookup to it, so there's no outline along a seam. Overlapping views just draw later over earlier (minimap). A full-screen view after an inset would clear the inset, so draw insets last. 2D clipping is `ctx.save/clip/restore` (`apply2dClip`). `mouse_ray()` uses `lastViews` (the views drawn last frame): the topmost containing the cursor; in mouse mode 2, the middle of the first view.

**Palette**, PICO-8 style, in two layers:

- `palette`: a global array of 32 colors (0xRRGGBB), defaulting to the PICO-8 extended palette. Changing an entry recolors everything next frame.
- `pal(a, b)` / `pal()` / `palt(i, on)`: a **per-draw** remap and transparency. It is captured at each draw call.
- In the shader, transparency is checked against the original index. Then comes the remap, then the palette lookup.

**Fog** (asked for by the owner, 2026-11-11, from Claude's suggestions; he turned down face shading and torch light, so the "no shading or lighting" decision above stands): `fog(c, near = 8, far = 24)` / `fog()`. Draw state like `pal` and `outline` (baked into each draw in `take`; `reset` turns it off), so the HUD and anything after `fog()` stay clear. The color goes through `remap` when `fog` is called, like `bg`. In the shared shader (`PAL_GLSL`'s `writePixel`): the distance is `length` of the view-space position (a varying from each vertex shader), so fog doesn't shift as the camera turns; `t = (dist - near) / (far - near)` against a **4×4 ordered (Bayer) dither** on `floor(gl_FragCoord / uPix)`, so the pattern stays at the 256 scale at 2×/3× and doesn't crawl. A fogged pixel takes the palette color exactly (no blending: every pixel stays a palette color) and writes **no outline and face direction 0**, so fogged shapes cast no outlines and get no crease lines; an unfogged draw in front still outlines against the fog. Pure dither to one color, without stepping through darker shades first (a `dark[i]` table was offered and not chosen). Demo: **Fog Valley** (`demos/fog.b3d.json`, the Starter cart's assets, a 96×10×96 valley built in `_init` from a height function, tank controls, `cam_orbit`, X cycles mist / dusk / swamp / night / off).

**Two-color sky** (asked for by the owner, 2026-11-11, from the same suggestions as fog): `bg(sky, horizon)`; `bg(c)` as before. Tied to the **horizon, not the screen** (Claude's choice, changeable): each pixel's view ray against world up gives its elevation; at or below the horizon it's `horizon`, from 45° up it's `sky`, and in between the same 4×4 dither as fog at the 256 scale. So it stays put when the camera tilts, and fog in the horizon color meets it exactly. It's `createSkyMesh` in `js/core.js`: a full-screen quad in the scene with `renderOrder` -1e9, no depth test or write (so the outline pass still treats it as background, and `palt` holes show it), writing no outline info; `drawView` shows it only for views whose `bg` had two colors, setting the colors per view (split-screen views can differ). Both colors go through `remap` when `bg` is called, like `bg(c)`. Outside every view (`clip` gaps) the screen is still cleared to the plain `bg` color. Games with one-color `bg` render byte for byte as before.

**Outlines** (agreed with the owner):

- `outline(c)` / `outline()`, per-draw state like `pal`, **off by default**. The color is a palette index and goes through the current `pal` remap at draw time.
- They're screen-space and 1 pixel wide, and work the same for maps, primitives and the future spr. Every shader also writes a second output (outline index + 1, draw id); a full-screen pass in `createOutlinePass` (`js/core.js`) then paints a pixel with the outline color of a 4-neighbor that is outlined and in front of it.
- **Every visible edge of a map is outlined** (the owner asked for this: a box-shaped map shows all its visible edges, and a divot in a cliff is outlined). Two rules inside the same map:
  - **Creases:** map pixels also record which way their face points (direction 1-6 in the info target's alpha; 0 for primitives). Neighboring pixels facing different ways get a line, which covers both outside and inside corners, like the foot of a pillar. Only the pixel with the larger direction index takes the line, so it stays 1 pixel wide. Grid lines between blocks on one flat surface get no line.
  - **Depth jumps:** where one part of the map is in front of a parallel part behind it, the pass extrapolates the neighbor's surface one pixel (1/z is linear across a flat face) and outlines where this pixel sits well behind it.
- Primitives only get outlined against other draws and the background, never inside themselves (so a low-poly sphere doesn't show its facets).
- **`outline(c, false)`: outer outline only** (the owner asked, for round voxel models; it applies to maps too, and drops overlap lines as well as creases). Per-draw state like the color; `outline(c)` turns inner edges back on and `outline()` resets both. Each material has a `uInner` uniform; when it's 0, `writePixel` stores direction **7** instead of the face direction, and the outline pass skips any pair of pixels from the same draw when the neighbor is a 7 (no crease, no depth jump), so only edges against the background or other draws remain. No extra texture fetches. Default output is pixel-identical to before at 1× and 3×.
- The pass fetches each depth and info texel once per neighbor; keep it that way. Under SwiftShader (CPU rendering), the demo runs at the same frame rate with outlines on or off.
- Background is detected by the depth buffer still holding its cleared value. Don't clear the color with alpha 0: three.js premultiplies the clear color, which turns the background black.

**Vox models** (agreed with the owner):

- Up to 256 models, numbered 0-255 (raised from 64 by the owner), edited in the **Vox** tab (the old Spr tab is now **Tile**). Each is 8×8×8 voxels; one byte per voxel, 0 = empty, else palette color + 1, so black (color 0) stays usable. Index `x + 8 * (y + 8 * z)`, y up, the model's **front is +z**.
- **8 voxels = 1 block**: unscaled, a model fills exactly one block.
- `vox(n, x, y, z, pitch, yaw, roll, sx, sy, sz)`: everything after the position is optional; `sy`/`sz` default to `sx`. Angles are in turns, in the **same order as maps** (yaw, then pitch, then roll). World = pos + R · S · (local − pivot) / 8.
- Each model has a **pivot** in voxel units (default `[4, 0, 4]`, bottom center), set in the editor. It's the point placed at x, y, z and the center of rotation and scaling, so a leg with its pivot at the hip swings correctly.
- **Animation is model swapping**, PICO-8 style, plus composing characters from parts in code. A skeleton/rig editor was considered and set aside as not worth the effort. The editor helps with frames: Duplicate (appends a copy), onion skin (previous model shown faintly in the grid and 3D view), and a Play button that loops a range of models in the preview.
- `pal`, `palt` and `outline` apply. Vox meshes write face directions like maps, so outlines show their edges and creases.
- Models have no collision; games keep using spheres and `mgetw`.
- Editor: layer grid (top view by default, +z down; see **Editor planes, undo** for Front/Side), click a face in the 3D preview to add (right-click or the Erase tool removes), Pencil/Erase/Fill/Pick tools, mirror across x, name, pivot. Add and Duplicate append at the end, so existing numbers never change; Delete renumbers later models (with a confirm).

**Scenes** (designed with the owner, for placing many copies of a map, e.g. a house five times, and for laying out levels):
- `map_copy(m)`: a new map (appended, returns its number) with its own copy of m's blocks and m's origin, pos and angle. `map_stamp(src, dst, x, y, z)`: copies src's non-empty blocks into dst with src (0,0,0) at dst (x,y,z), grid-aligned, no rotation; empty src cells leave dst alone, blocks past the edge are dropped.
- `map_box(m, x0, y0, z0, x1, y1, z1, t)` (the owner agreed, for building levels in code, mostly by AI chatbots): fills the grid cells between two corners, both included and in either order like `rect`, with tile t (`& 255`; 0 carves); coordinates are floored, cells past the edge skipped, the map marked dirty once. Checked: a floor, a box with reversed corners and one cell carved, and a box clipped at the edge with fractional corners give the expected counts.
- `map_reload(m)` (the owner's request and rules): copies the cart's blocks (`templates`) back into cart map m and marks it dirty. **Only cart maps** (0 to the cart's map count - 1); copies (`map_copy`, scenes) and `map_new` maps are never touched, and passing one throws a plain error. **Blocks only**: pos, angle and origin stay (the owner agreed: snapping a moving map back mid-ride would surprise). No argument (or null) reloads every cart map. Bumper Arena reloads its arena each round instead of rebuilding it with `mset`.
- A **scene** (Scene tab, cart `scenes`) is `{ name, maps: [{ m, pos, angle, name? }], vox: [{ v, pos, yaw }] }`. Map placements: pos is where the map's origin goes (same as `map_set_pos`), angle `[pitch, yaw, roll]`, an optional name. Vox markers: just number, position and yaw (the owner's choice); the engine never draws them, they're data for the game (start, pickups...). Scenes have no bg or camera (left to code, the owner's choice).
- `scene_load(n)` (the owner picked the name) returns `{ maps, named, things }`: `maps` = numbers of fresh copies in editor order, `named` = `{ name: map number }` (a repeated name: the later one wins), `things` = `[[v, x, y, z, yaw], ...]`. **Copies always come from the cart's maps as loaded** (`templates` in `js/engine.js`, decoded once), even for a map placed once, so reloading a level is undamaged and templates never need protecting. Each `scene_load` first frees the previous load's copies (`freeSceneMaps`: slots set to `null`, trailing nulls popped, so reloading the same scene gives the same numbers when nothing was made after it); `getMap` on a freed slot throws a plain message. `reset()` (Restart) clears it all.
- Editor (`setupSceneEditor` in `js/ide.js`, `setScene`/`pickItem`/`planePoint`/`frameBox` in `js/preview.js`): one list (maps, then vox markers; the selection `sceneSel` indexes that flat list), a 3D view (click selects, dragging a thing moves it on the flat plane at its height, snapped to the step; dragging empty space orbits, right/Shift-drag pans), fields for position/angle/yaw/name, nudge and quarter-turn buttons, keys (arrows move along the world axis nearest the view's right/forward, PgUp/PgDn, R, Delete). Meshes are cached per map/vox number and the cache is dropped whenever the tab opens. **Deleting a map or vox model removes its placements/markers in every scene and renumbers later ones** (`sceneRemoved`). Carts without scenes don't carry the field (`normalizeCart` drops an empty list), so older carts and exports are unchanged.

**Editor planes, undo, voxel edges** (asked for by the owner, for the Map, Vox and Scene tabs):
- **Planes:** Map and Vox have Top / Front / Side buttons. `slice(axis, w, h, d)` in `js/ide.js` turns a grid cell (column u, row v, layer L) into `[x, y, z]`: Top = layers along y, +x right, +z down (the old view); Front = layers along z, +x right, +y up (seen from +z, the vox front); Side = layers along x, +z right, +y up (seen from -x). Painting, fill, clear/fill layer, ghost (the layer before), onion skin, the pivot cross and the preview's red layer box (`layerLines` in `js/preview.js`) all follow the plane; the Map grid shows tiles' top faces in Top and side faces otherwise. The Scene tab's "Drag on" picks the plane a dragged thing slides on: Ground (x, z at its height, the old behaviour), Front (x, y at its z) or Side (z, y at its x); `planePoint(cx, cy, value, axis)`.
- **Undo/redo:** `history(take, put, undoBtn, redoBtn)` in `js/ide.js`, one per tab (`mapHist`, `tileHist`, `voxHist`, `sceneHist`), up to 100 snapshots taken just before a change: Map snapshots one map (size, origin, blocks; a paint stroke, fill/clear layer, resize), Tile one tile's three faces (`tileSnap` before a stroke, box, fill, Copy to all or Clear; `tileCommit` keeps it only if the tile changed; added later at the owner's request), Vox one model's voxels (a stroke, a fill, a click in the 3D view, Clear), Scene all scenes as JSON plus the open scene and selection (add, duplicate, delete, drag, nudge, turn, new/duplicate/delete scene, and one step per visit to a text field). A stroke saves only when it first changes something. Undo shows the map/model it changed. Buttons plus **Ctrl/Cmd+Z**, redo **Ctrl/Cmd+Shift+Z** or **Ctrl+Y**, only while the tab is open and no text field has focus (fields keep their own undo). Not saved in the cart; loading a cart clears it, and deleting a map or vox model clears the map/vox and scene histories (numbers shifted). Names, the vox pivot and map origin typed into fields aren't undo steps in Map/Vox.
- **Map tools** (asked for by the owner): `#mapTools` picks `mapTool`: pencil (the old drag painting), rect / rectfill (drag on the grid; `mapRect` holds the corners and `drawGrid` overlays what will be painted at 0.8 alpha with a yellow box; committed on pointerup, `rectCells`), fill (`floodLayer`, 4-connected on the slice being edited, in any plane) and volfill (`floodVolume`, 6-connected through the whole map, from the clicked cell of the current layer). The right button (or tile 0) is the value for every tool; one undo snapshot per action; fills that change nothing save nothing. Checked against expected cells computed separately: a 5x4 rect outline (14 cells, nothing else touched), a fill inside it (6), a rect fill dragged backwards, a right-drag erase, vol fill of the castle's open air (1,500 blocks) and a right-click vol erase of a solid (160) equal to a 3D flood fill, six undos restore, a fill in the Front plane stays on its layer; no page scroll at phone width.
- **Shift and Duplicate** (asked for by the owner): a Shift row (`.shiftpick`, six buttons with `data-shift="axis,dir"`, wired by `setupShift`) in the Map toolbar, the Vox layer bar and the Scene toolbar. Map and Vox use `shiftGrid(data, w, h, d, axis, dir)`: one cell along the axis, **wrapping** round (the owner's choice), blocks only (origin and pivot stay); one undo snapshot each. The Scene tab's moves every placement and marker by the Step (no grid, so no wrap), and the Step select moved from the selection panel to the toolbar so it's visible with nothing selected. Map **Duplicate** appends a copy (blocks, size, origin; name + " copy"), like Vox's. Checked: +Y twice on Village's house equals a wrapped shift exactly (the roof comes round to the bottom), other maps untouched, −X wraps, three undos restore; Duplicate copies the blocks and selects the copy; a vox +X then −Z is exact and 8 more +X come full circle; a scene +Z by 0.5 moves all 11 things and leaves the other scene alone, undo restores; no page scroll at phone width; the older editor and Scene tab tests still pass.
- **Voxel edges:** a Vox tab checkbox outlines every voxel in the 3D view (`voxelEdges`: 12 edges per filled voxel; the model's material has a polygon offset so the lines sit on its faces).

**Text and UI** (agreed with the owner): `print(str, x, y, c, oc, sx, sy)` draws on a 2D overlay canvas on top of the 3D view, in screen pixels. The font (`js/font.js`) uses 7×10 cells: 5-wide glyphs, 7-tall capitals, 2-row descenders, a 1-pixel margin all round, upper and lower case and all printable ASCII. Glyphs are written as `#`/`.` rows in that file, so they're easy to edit. `oc` is an optional outline color (8-direction ring, drawn under all the text first); leaving it off means no outline. Both colors go through `pal`. `sx`/`sy` are whole-number scales (`sy` defaults to `sx`; the owner asked for both so titles can be stretched); the outline scales with the text (one font pixel thick). Pass `oc` as `null` or `-1` to scale without an outline. `print` returns the x just past the text, like PICO-8. `rect(x0, y0, x1, y1, c)` (outline) and `rectfill(...)` (filled) draw on the same 2D layer, corners included and in either order, PICO-8 style. Text and rectangles stack in call order.

**Pause menu** (asked for by the owner): Enter, NumpadEnter or P (button 6 in `KEYMAP`) pauses, handled by the engine, not the game. While paused, `_update`/`_draw` don't run, `time()` doesn't advance and the audio context is suspended. The menu is drawn on **its own canvas** (`menuCanvas`, created by the engine right after the overlay, `pointer-events: none`, shown only while paused) in the default palette, so it's readable whatever the game did to `palette`. The game's overlay is left untouched while paused (`_draw` doesn't run), so nothing is read back with `getImageData`. That readback used to be how the overlay was frozen, and on a real phone the first one (after each start or restart) left the menu invisible except for single frames, probably because reading a canvas back makes the browser move it off the GPU. Keep pixel readback out of the pause path. Items: Resume, Restart, Screenshot, Capture GIF (below), Capture cover (IDE only, see **Cover screen**), Resolution (see below). **Restart is soft** (the owner asked, after a page reload dropped fullscreen and broke the touch controls): boot's `restart()` calls `engine.reset()` (maps rebuilt from the cart, palette, `pal`/`palt`, `bg`, outline, camera, time, mouse mode, input, pause and sound back to the start; resolution, mute and fullscreen kept) and runs the cart function again, `_init` included. It works the same in the IDE and in exports, because both hand `Blocko3D.start` the cart as a **function returning its hooks** (`cartFunctionSource` in the player, a `function () { … }` wrapper in the export), so each run gets fresh top-level `let`/`const` (as a plain script they'd clash on a second run). The wrapper adds no line, so error line numbers still match. `location.reload()` is only the fallback when `start` was given plain hooks. Screenshot composites the GL canvas (`preserveDrawingBuffer: true`) and the game's overlay at the active resolution with no menu, and downloads `<slug>_<timestamp>.png`. The page's pause button (see **Game page** below) presses button 6 once. For 15 updates (0.25 s) after pausing, the menu ignores choosing (`menuAge`), so a doubled press can't resume straight away (a reported phone bug: the first pause tap unpaused at once). Pausing calls `audio.suspend()`, which sets `held`: while held, `unlock()` (run on every key press and click) creates the context if needed but never resumes it, and a resume still in flight when the game pauses suspends again when it lands (`wake`). Only `audio.resume()` (Resume) brings sound back.

**Capture GIF** (asked for by the owner, like PICO-8's F9): the pause menu item saves the last **10 s of game time** as `<slug>_<timestamp>.gif`, 256×256, looping. Recording is always on (`recordFrame`, after each `endDraw`): when at least 2 updates have passed since the last capture (30 fps of game time; fewer when the device draws less often), the GL canvas (scaled to 256, nearest) and the overlay are drawn into a private `willReadFrequently` canvas, read back with `getImageData`, and stored as palette indices in a ring of 300 `Uint8Array`s (~20 MB, made on first use) with the frame number. Only that private canvas is read back, never the overlay or menu canvas, and never while paused, so the pause-path rule above holds. Indices go into one shared color table (up to 255 colors; past that a new color maps to the nearest one already in it); `reset()` clears it all. Nothing is recorded in step mode (`b3d shot/run`). About 0.8 ms per capture under SwiftShader. Saving keeps the frames from the last 10 s, and `GifWriter` (`js/gif.js`, our own LZW encoder, no dependency) writes them a few at a time (`setTimeout` every 30 ms, progress shown as the menu note): each frame after the first is only the rectangle that changed, unchanged pixels inside it transparent, disposal 1, identical frames merged; delays in hundredths of a second come from the frame numbers (3, 3, 4, …), so the GIF plays at the game's speed. The castle demo's 10 s came to about 2 MB, encoded in 0.5 s.

**Resolution** (agreed with the owner): the pause menu's Resolution item (left/right or select) sets the 3D view to **1×, 2× or 3×** (256/512/768 square). Only these three, by the owner's choice. The 2D overlay (`print`, `rect`) always stays 256. The choice is stored per device in `localStorage['blocky3d.res']`, and screenshots save at the active size. Changing it while paused re-runs `_draw` once to repaint the frozen frame.
- 1× uses the original single outline pass. 2× and 3× keep outlines one 256-pixel thick (k real pixels) with option 1 from the design talk: the edge pass writes a 1-pixel **edge mask** to a float target (`uMode = 1`: outline color + 1, outlined surface's distance, its draw id, edge kind); two **grow passes** widen it by k − 1 (across, then down; nearest surface wins; creases grow only toward +x/+y so they stay k wide); a **paint pass** colors a pixel only where the kind allows. Kind 1 (over something else) goes onto background or another draw farther away; kind 2 (depth jump in one draw) onto the same draw well behind; kind 3 (crease) onto the same draw. So outlines spread over what's behind an object, never into it.
- 2×/3× need `EXT_color_buffer_float` (float render targets); without it the Resolution item is hidden and the game stays at 1×.
- Spheres use 24×16 segments so they look round at 3×. `line3` stays 1 real pixel wide.
- Performance: under SwiftShader (CPU rendering) frame time grows with pixel count (about 23/116/247 ms for 1×/2×/3× in the demo); on a real GPU 768² is small.

**Sound** (asked for by the owner): PICO-8-style SFX in `js/audio.js`, shared by the engine and the IDE.
- 64 sounds × 32 notes; each note has pitch 0-63 (33 = A 440 Hz), wave 0-7 (triangle, tilted saw, saw, square, pulse, organ, noise, phaser), volume 0-7 and effect 0-7 (none, slide, vibrato, drop, fade in, fade out, arp fast, arp slow). Speed: each note lasts speed/120 s. Loop: notes loopStart up to loopEnd repeat.
- **Saved as a string** (the owner wanted Playload-like strings): 166 hex characters, `SS LL EE` then `PP W V E` per note. The cart's `sfx` is an array of these strings (null for empty slots, trailing empties dropped).
- Sounds are synthesized in JS to a 22050 Hz buffer (cached per string) and played with Web Audio on 4 channels. Looping uses the buffer source's loop points. `sfx(n, ch, offset, length)`, `sfx(-1[, ch])` stop, `sfx(-2, ch)` releases a loop, and `sfx(str)` plays a string directly.
- Browsers block audio until a user gesture: the engine unlocks on keydown/pointerdown, and the IDE's iframe has `allow="autoplay"`. Sounds requested before the unlock are dropped, not delayed.
- Sfx tab: slot list, Play (Space), speed, loop, a brush (wave, volume, effect) applied when drawing in the pitch graph, separate volume graph and wave/effect rows, a playback cursor, and a string field to copy or paste a sound.

**Music** (asked for by the owner):
- 64 **patterns**; each has 4 channels (an sfx number, or empty) and flags: loop start, loop back (jump to the nearest loop start at or before it, else the pattern the song started on), stop (end after it). Saved as 9 hex characters: flags (1 = loop start, 2 = loop back, 4 = stop), then 2 hex digits per channel (00-3f, or 40 = empty). The cart's `music` is an array of these strings.
- A pattern lasts as long as its longest **non-looping** sound's 32 notes (if all loop, the first channel's). Looping sounds repeat their loop to fill it. The song also ends at an empty pattern or after pattern 63.
- Playback: each pattern's channels are mixed into one buffer (`renderPattern`, cached) and scheduled back-to-back on the audio clock, 0.4 s ahead, by `SfxPlayer.music`. **Music has its own 4 voices** separate from the 4 sfx channels, so effects never cut out the song (a simplification from PICO-8, where they share channels). `music(n, fade)` fades in; `music(-1, fade)` fades out. A music request made before the browser allows sound is kept and starts on the first key press or click. Pausing suspends the audio clock, so music pauses too.
- **Music tab:** pattern list (playing pattern highlighted), Play (Space) from the current pattern that follows the song, flag checkboxes, 4 channel cards (enable, −/+ sound number, a mini pitch view with a playhead, click or Edit sound to open it in the Sfx tab), and the pattern length.
- **Scale snapping** in the Sfx tab: "Snap to scale" with a root note and one of 9 scales (minor/major pentatonic, major, minor, harmonic minor, dorian, mixolydian, blues, whole tone). The default when enabled is **C minor pentatonic**, like PICO-8. Drawn pitches snap to the nearest scale note (ties go down), scale rows are highlighted in the pitch graph (root brighter), and "Snap this sound" moves an existing sound's notes onto the scale. Settings are saved in the cart as `scale: {snap, root, type}`; the engine ignores them.

**Input and gamepads** (asked for by the owner, PICO-8 style): `btn(i, p)` / `btnp(i, p)` with player p 0-3 (default 0). **Player 0 = the keyboard OR the first connected gamepad**; the 2nd, 3rd and 4th connected gamepads are players 1-3, ordered by the browser's gamepad slot (gaps skipped), so if the first pad is unplugged the next one becomes player 0. Pads are polled once per `_update` step (`pollInput`). Standard mapping: d-pad (12-15) or left stick (axes 0/1, deadzone 0.5) for directions; O = A or X (0, 2); X = B or Y (1, 3); Start (9) = button 6, pause, from any player. Any player can drive the pause menu.
- **All gamepad buttons** (the owner asked to keep counting up): 6 Start (still pauses), 7 A, 8 B, 9 X, 10 Y, 11 LB, 12 RB, 13 LT, 14 RT, 15 Select, 16 L3, 17 R3, 18 Home (`EXTRA` in `js/engine.js` maps them from the standard layout). 0-5 keep combining buttons (O = A or X, X = B or Y) so keyboard and pad games stay compatible. Buttons 7-18 have no keyboard keys. Triggers count as pressed past the browser's threshold; there's no analog trigger value yet.
- **`stick(i, p)`** (the owner's design): i = 0 left, 1 right; returns `[x, y]`, -1..1, **right and down positive** (screen and browser convention; Claude's choice, changeable). Round dead zone 0.15, rescaled so values start at 0 just outside it. When the left stick is centered, `stick(0)` falls back to the player's d-pad/arrow buttons (diagonals normalized to length 1), so analog code works on a keyboard. The demo moves with `stick(0)`.
The IDE iframe has `allow="autoplay; gamepad; fullscreen"`. Browsers only expose a pad after one of its buttons is pressed, and pad presses don't count as a gesture for unlocking sound. `btnp` has no auto-repeat (PICO-8's does).

**Mouse and touch** (designed with the owner): `mouse_set_mode(m)`: 0 off (default: mouse and touch ignored, so existing games are unaffected), 1 click, 2 capture (Pointer Lock on the overlay canvas).
- Buttons are **19 left, 20 right, 21 middle** of player 0, folded into `btn`/`btnp`. The context menu is blocked in modes 1 and 2.
- `mouse_pos()` → `[x, y]` in 256 screen pixels (overlay `getBoundingClientRect`), can go outside 0-255 when the cursor is off the screen (only seen in exports; in the IDE the iframe stops getting events at its edge); frozen while captured. `mouse_delta()` → `[dx, dy]` raw CSS pixels since the last `_update` (movementX/Y; fractional for touch). `mouse_wheel()` → notches since the last update (deltaY/100 for pixel mode, /3 for lines), down positive. `mouse_locked()`. Deltas and wheel are accumulated from events and snapshotted in `pollInput` (`takeMouse`).
- Mode 2 arms capture: the next click on the game locks, and that click is swallowed. **Losing the lock (Esc, alt-tab) pauses the game**; pausing exits the lock and Resume requests it again, **but only if the last press was a mouse** (`lastPointer`, from every `pointerdown`): on a phone the Resume tap counts as a gesture, the browser granted the lock, and with the pointer locked every touch went to the game screen, so the d-pad and drag-to-look died after the first pause (reported on a real phone; restart fixed it until the next pause). If the browser refuses, e.g. Chrome's ~1 s cooldown after Esc, it stays armed and the next click locks).
- Touch (pointer events with `pointerType !== 'mouse'`, one finger tracked): mode 1 a tap is button 19 at that spot; mode 2 dragging gives deltas (no button). The overlay gets `touch-action: none` in modes 1/2.
- The pause menu is clickable/tappable in modes 1 and 2: hover selects, click chooses (`menuRects` from `drawMenu`).
- **Short presses are latched** (`tapped[]`): a key or mouse press that starts and ends between two updates still reads as down for one update, so `btnp` never misses it.
- `mouse_ray()` → `[ox, oy, oz, dx, dy, dz]`: the ray from the camera through `mouse_pos()` (the screen center in mode 2, like a crosshair), direction normalized, built from the camera as last set (`camPos`, `camLook`, fov) with a spare three.js camera and `unproject`, so it matches the render. `mray(m, ...mouse_ray())` is the block under the cursor.
- In mode 2, mouse movement only counts once the mouse is captured (touch drags always count): before that, moving the mouse to the game to click would spin a mouse-look view. Found while building the First Person demo.
- Audio still unlocks on any pointerdown in every mode.
- **Deferred (discussed with the owner): `mouse_pick()`.** Draw calls would return their draw id, and `mouse_pick()` would read the id under the cursor from the info target (pixel-exact clicks on vox models and primitives, one frame late, a 1-pixel `readPixels` only when called). Set aside until games want it; distance checks cover most cases.

**Game page: touch controls and system buttons** (asked for by the owner, PICO-8 style): `js/shell.js`, bundled into the runtime, builds the page around the game for both Run (`player.html`) and exports, so they match. `install()` calls `mountShell()` when no canvas is passed, and `wireShell(engine)` connects it. It's plain HTML and CSS around the canvases, never drawn on the game screen; the style sheet goes first in `<head>`, so an exported `index.html` can restyle it.
- **Layout** (CSS grid, by `orientation`): landscape puts the d-pad left of the screen, O and X right, system buttons at the top of the right column; portrait puts the screen on top, the system buttons under it, then the d-pad and O/X. The screen stays square and as big as fits (`--g`), safe areas respected.
- **System buttons, always shown (desktop too):** pause (presses button 6 once through `engine.setButton`), mute (`engine.setMuted`, the audio player's master gain; stored per device in `localStorage['blocky3d.mute']`, muted sounds still play silently), fullscreen (the whole page, so the controls stay; hidden where the browser has no fullscreen, e.g. iPhone Safari). They never take keyboard focus, so Space/Enter keep going to the game. A finger acts on `pointerup` (a user gesture, which fullscreen needs) and a mouse or keyboard on `click`; anything within 500 ms of the last activation is dropped, so one tap is always one action.
- **Touch controls** show only with `pointer: coarse` or after any touch on the page (`html.b3d-touch`), so a touchscreen laptop gets them on its first tap. The d-pad is one touch area with 8 directions (thumb can roll onto diagonals, center dead zone); O and X are separate buttons; several fingers work at once. They press buttons 0-5 of player 0 directly (`engine.setButton`, the `held[]` array), no fake key events.
- The IDE's own touchpad is gone; its iframe has `allow="autoplay; gamepad; fullscreen"`.
- **`touch_set_mode(n)`** (asked for by the owner, who preferred this name to `mobile_control_set`): the left touch control is 0 d-pad (default), 1 analog circle, 2 left/right, 3 up/down. It's the same `.b3d-dpad` element with `data-mode`; the touch math in `dpadUpdate` changes per mode. **Analog:** fixed circle, no drag needed; the vector from its middle, divided by 0.9 of the radius and capped at length 1, goes to `engine.setStick` (`touchStick`), which `pollInput` uses as player 0's left stick when the pad's is centered, so `stick(0)` applies the usual dead zone and rescale; past 0.5 on an axis it also presses that arrow button, so d-pad games still work; a knob (`--kx`/`--ky`) shows the finger. **Left/right** and **up/down:** two big buttons, each half of the area (a thin middle strip presses nothing). The engine owns the mode and tells the page through `onTouchMode`, sending 0 while paused (so the menu always gets the d-pad) and the game's mode again on Resume; `reset()` (Restart) sets 0. The cover screen's stand-in hands its `onTouchMode` to the real engine when the game starts. Tilt Maze and Third Person call `touch_set_mode(1)` in `_init`.

**Cover screen** (asked for by the owner, like PICO-8's label): exports call `Blocko3D.play(cartData, cartFn)` (boot.js) instead of `install` + `start`. It mounts the shell and draws the cart's `cover` (a 256×256 PNG data URL; without one, the cart name on a dark blue card) with a play button on the overlay canvas, using 2D only: **no WebGL context, no cart code, no audio until the player starts**, by clicking or tapping the screen, any key (not modifiers, Tab, Esc or F-keys), A/B/X/Y or Start on a gamepad (polled with requestAnimationFrame), or the touch d-pad/O/X. Until then the shell is wired to a stand-in object: mute works (written to `localStorage['blocky3d.mute']`, which the engine reads), pause does nothing, other buttons start the game. Starting calls `install(cart, { canvas, overlay, wire: false })`, unlocks audio inside the same gesture, then `start(cartFn)`; a WebGL failure shows the plain error on the cover's canvas. Always on, not optional (the owner's choice). **Capture cover** is a pause-menu item only when `createEngine` gets `onCover`, which only `player.html` (the IDE) passes: it composites the 3D canvas scaled to 256 plus the overlay, sends `{ type: 'cover', png }` to the IDE, which stores it as `cart.cover`, autosaves, and shows a thumbnail with Clear under the game. The castle's cover is `demos/castle-cover.png` (its cart is generated), read by `tools/build-demo.mjs`; the other demos have `cover` in their `.b3d.json`. The demo covers were captured by a throwaway script: the exported game run a few seconds, then the 3D view with the demo's name printed at scale 3 on top. `normalizeCart` keeps `cover` only if it's a PNG data URL.

**Save data** (asked for by the owner): `save(value)` / `load()` store one JSON value per game in `localStorage` under `blocky3d.save.<slug of the cart name>`, up to 64 KB. `save(null)` deletes it. Web pages can't silently write real files, so the browser's storage is the "file". It works in the IDE, from `file://` and on itch.io. The IDE shows the current save under the game with a Clear button (the player posts `save` when a game saves). Renaming the cart changes the key.

**`freeze(n, fn)`** (the owner's design, instead of PICO-8's `flip()`): for the next n updates the loop calls `fn` instead of `_update` (nothing when `fn` isn't a function); `_draw` runs as usual, so with game state untouched the picture holds still and `fn` can drive an effect (Bumper Arena's camera shake). `frames`/`time()` keep counting, input is still polled, pausing holds the count, a new call replaces the current freeze, `freeze(0)` ends it, `reset()` clears it. A real `flip()` was discussed and rejected: JavaScript can't block, so it would have to be `await flip()` inside `async` functions, and the owner doesn't want developers dealing with that.

**Helpers** (the owner picked them from a review of what the demos repeat): `dist(a, b)` (arrays of any length or objects with x, y and optional z; missing values are 0; one function instead of `dist2d`/`dist3d`, since in a y-up world "along the ground" is x/z: `dist([a.x, a.z], [b.x, b.z])`), `dir3(yaw, pitch)` (unit vector in the engine's axes), `yaw_to(dx, dz)` (the inverse; same as the old `atan2(dz, dx)`, whose argument order was a trap), `angdiff(a, b)` (shortest turn from a to b, -0.5..0.5), `cam_orbit(target, yaw, pitch, dist)` (camera at `target - dir3(yaw, pitch) * dist`, looking at target: **yaw and pitch are the camera's view direction**, the same meaning as `dir3`, so looking down from above is a negative pitch; the owner confirmed this, rather than a positive "camera sits above" pitch), `textw(str, sx)` and `printc(str, y, c, oc, sx, sy)` (centered across the clip area, or the screen). **`mpush(maps, x, y, z, r)`** (the owner chose the fuller of two designs): `maps` is a number or a list; up to 3 passes over the list with the sphere query (stopping early when nothing moves), exactly what the demos' hand-written loops did (checked equal on 300 random spots); returns `[x, y, z, nx, ny, nz, ground]` with n the normalized sum of all pushes (zeros if none) and `ground` the map whose push was most upward with ny > 0.5, else -1. Third Person, First Person, Tilt Maze (bounce off n) and Racing use it. **`lerp(a, b, t)`** (the owner's choice: numbers and arrays, not angles; use `angdiff` for those): arrays blend element by element; a number `b` with an array `a` blends every element toward it.

- **Round 3** (2026-11-11; the owner asked for these three, from Claude's review of the repo; the details are Claude's choices, changeable):
  - **`b3d serve <game> [--port n] [--open]`** (`cli/cmd-serve.mjs`): an HTTP server on `127.0.0.1` only (port 8030, or the next free one up to +20 when `--port` isn't given). It **polls** the folder every 250 ms (paths, times and sizes; skips dot files, `node_modules`, `.b3d.json` files and `b3d.d.ts`) rather than `fs.watch`, because recursive watching isn't reliable on Linux before Node 20 and polling behaves the same everywhere; it rebuilds once two polls agree (an editor's save can take several writes). Rebuild = `loadGame` + `checkGame`: errors keep the running game and go to the page (a banner) and the terminal; success bumps a version that the page hears through server-sent events (`/events`) and reloads for. **A reload restarts the game from `_init`** (no hot state swap: simplest, and like PICO-8's Ctrl+R). The page is the runtime bundle plus `install` + `start` with the cart's code evaluated as `cartFunctionSource(code)` with `//# sourceURL=main.js`, so error lines match `main.js`; no cover screen (`play` is skipped), audio unlocks on the first key or click. `printh`, `save` and errors are POSTed to `/log` and printed, errors as file:line through `errorText` and the game's `where`. Nothing is written to the folder except refreshing `b3d.d.ts`.
  - **Editor autocomplete** (`cli/editor.mjs`): `b3d.d.ts` is made from `API_SECTIONS` (the same parsing as the IDE's `apiList`; the Game loop and Command line sections are left out, since `_init`/`_update`/`_draw` are the game's own). One `declare function` per documented signature (overloads), every argument and return typed `any` (names, counts and docs are the point; types would be wrong somewhere, and `checkJs` is off so nothing is underlined); `[x, y, z]` arguments are named `xyz`; signatures that come out the same (`sfx(n)`, `sfx(-1)`) are one declaration with both descriptions; `palette` is a `declare var`. Written by `new`, `unpack` (always rewritten) and `serve`; `jsconfig.json` (`main.js` + `b3d.d.ts`, `checkJs: false`) only when missing. `npm test` checks the names equal the engine's `Object.keys(engine.api)` both ways, so an API change without docs fails CI; all eleven demos type-check with no unknown globals.
  - **Text maps** (`maps/N-name.txt`, in `cli/folder.mjs`): a `legend` (character, tile number, optional name), then layers `y0` up, each `d` rows from z0 (back) to the front, `w` characters from x0 (the Map tab's Top view, the same layout as vox files). `.` empty; `#` comment; `y` is never a legend character, since `y3` is a layer heading. **Missing layers are empty**, and unpack leaves out empty layers, so sky costs nothing. Unpack picks a tile's name's first letter (lower, then upper case) when free, else the next character from a 91-character pool (`MAP_POOL`), in tile-number order, so unpacking is deterministic; a map with more than 91 different tiles is written as `.bin`. Pack reads `.txt` or `.bin` (both for one map is an error) and compares either with a `.gen.js` like before. **Unpack now writes `.txt` instead of `.bin`**, and removes the old numbered `.bin`, so the first unpack of an existing folder changes its map files (same blocks).

**Choices Claude made that the owner hasn't specifically reviewed.** Treat them as changeable:

- The primitive names and signatures: `cube(x, y, z, size, c)`, `sphere(x, y, z, r, c)`, `line3(...)`.
- The extras: `printh`, the keyboard mapping (arrows/WASD, Z C N space for O, X V M for X), `time`/`t`, and math helpers with turn-based `sin`/`cos`. `sin` is **not** inverted like PICO-8's.
- `_update` runs at a fixed 60 per second. The loop is `stepOnce()` (input, pause menu or `_update`) and `drawFrame()`; `engine.step(n, draw = true)` (internal, for tools, not in the game API) stops the clock and runs exactly n steps, each drawn, as on a 60 Hz screen (`draw` false draws only the last); `step(0)` before `start` keeps the browser's clock from running any update first (the headless runner does this). `reset()` hands the loop back to the clock.
- `srand(n)` (agreed with the owner, for headless runs and seeded levels): `rnd` then uses mulberry32 seeded with `round(n * 65536)` (so fractional seeds differ, like PICO-8's 16.16); `srand()` and `reset()` go back to `Math.random`.
- Nothing is transparent by default.
