# BLOCKO3D engine notes

What an agent changing the engine, the IDE or the `b3d` tool needs every time: the architecture, the build, the tests and what's open. Read it in full before changing code. Two longer files hold the detail, to read in part as needed: **`docs/DECISIONS.md`**, every design decision agreed with the owner and why (read the part for what you're changing), and **`docs/TESTING.md`**, what was checked by hand for each feature. (It was the repo's `CLAUDE.md` until 2026-10-29; `CLAUDE.md` is now a short pointer, so agents that only make games don't load all this.) Making games instead? Read `MAKING_GAMES.md`.

## What this is

BLOCKO3D (renamed from blocky3D on 2026-10-29, the owner's choice) is a small, deliberately limited **3D** game engine for JavaScript with a **PICO-8-style developer experience**. The owner (Rocco, who makes games as Palo Blanco Games and knows PICO-8 well) designed it in conversation with Claude. It follows an earlier, heavier engine called Neptune, whose developer experience felt too involved.

Guiding principles. Keep them when adding features:

- **Everything is global.** You call `map(0)`, never `engine.map(0)`. Keep the API small and terse, in the PICO-8 naming style.
- **Limits are the point.** 8×8 textures, a 32-color palette, flat rendering, a square screen.
- **All in one place.** The IDE is one static web page: code, map editor, tile editor, docs, Run. No build step, no install.
- **3D, not 2D.** There are plenty of 2D fantasy consoles already.
- Rocco prefers the **simplest thing that works** over clever architecture.

**Current version: 0.1.0-alpha**, tagged `v0.1.0-alpha` (the first version for human testing). The version lives in `js/version.js` (shown at the top of the Info tab, in the IDE console, in the first line of exported game scripts and as `Blocko3D.VERSION`) and in `package.json`; `CHANGELOG.md` lists what each version has. To release: bump both, add a CHANGELOG entry, `npm run build`, commit, then tag `v<version>` and push the tag.

The site is live on GitHub Pages (built and deployed from `main` by `.github/workflows/pages.yml`): the IDE at https://paloblanco.github.io/blocko3d/ and the exported demos at https://paloblanco.github.io/blocko3d/standalone_demo/ (a list page; the castle is at `/standalone_demo/castle/`).

The design spec lives in a Claude Doc titled "BLOCKO3D Spec" (claude.ai artifact `JH2BMJck8VtrndcyhxTSB5`). This file (`docs/ENGINE.md`) and the code are the source of truth if they disagree.

**Rendering details**

- `THREE.ColorManagement` is disabled and output is linear, so palette hex values reach the screen unchanged.
- Shaders are `ShaderMaterial` and use dynamic indexing into uniform arrays, which needs WebGL2.
- Textures **must** stay `NearestFilter` with no mipmaps. Filtering would blend indices into unrelated colors.
- The shader samples texel centers computed from the face UV, so the atlas never bleeds between tiles.
- Each pooled draw object has its own material, and the remap, transparency, outline color and draw id are copied into it on every draw.
- The engine renders the scene into a 256×256 multiple-render-target (color + draw info) with a depth texture, then the outline pass draws to the canvas. The editor previews render straight to their canvas; the extra shader output is simply ignored there.

**Cart format (JSON)**

```
{ version, name, code, palette?, tiles: [null, {top, side, bottom, name?}...], maps: [{name, w, h, d, origin, data(base64)}],
  vox: [{name, pivot, data(base64, 512 bytes)}], sfx: [string or null, ...], sfxNames?: [string or null, ...],
  music: [pattern string or null, ...], scale?: {snap, root, type}, cover?: 'data:image/png;base64,...',
  scenes?: [{name, maps: [{m, pos, angle, name?}], vox: [{v, pos, yaw}]}] }
```

- Map data is flattened as `x + w * (y + h * z)`.
- Tile and sound names are optional (the owner's choice, for the `b3d` folder form and the IDE's Tile/Sfx name fields). Sound names sit in a parallel `sfxNames` list because sounds are plain strings; `normalizeCart` drops empty names and an empty list, so carts without names are unchanged.
- In tile textures, row 0 is the top row of the image. On side faces it is the top of the block. **On top and bottom faces, columns run along +x and row 0 is the -z edge**, the same as the Map tab's Top view (+x right, +z down), so a tile looks the same in the editors and the game (the owner reported they were reversed in z until 2026-11-10; `FACE_DEFS` in `js/core.js` maps v = 1 - z). Seen from below, a bottom face therefore reads mirrored left to right.

**Dependencies**

- three@0.170.0, in two places that must match: `package.json` (bundled into the runtime) and `vendor/three/three.module.min.js` (the import map in `index.html` points there; used by the editor previews in `js/preview.js`). `tools/check-vendor.mjs`, the first step of `npm run build`, stops the build if the vendored file isn't byte for byte the npm package's `build/three.module.min.js`. To upgrade three.js: change the version in `package.json`, `npm install`, copy that file to `vendor/three/`, and update `vendor/README.md`.
- **The IDE loads nothing from other sites** (the owner agreed, so it works offline): `vendor/` holds CodeMirror 5.65.18 (`lib/codemirror.js`, the javascript mode and the CSS, minified with esbuild from the npm package), three's prebuilt `three.module.min.js`, and IBM Plex Sans 400/500/600 and JetBrains Mono 400/600 (latin woff2 from `@fontsource` 5.x, `vendor/fonts/fonts.css`), with their licenses and a `vendor/README.md`. To upgrade one, replace its files and keep the versions in sync.
- esbuild, a dev dependency for building the runtime bundle.

**Build workflow: run `npm run build` before every commit, for any change, not just engine changes.** Run `npm install` once first. The build rewrites, and you commit with your change:
- `runtime/blocko3d.runtime.js` (from `js/core.js`, `js/engine.js`, `js/font.js`, `js/audio.js`, `js/gif.js`, `js/shell.js`, `js/boot.js`, `js/version.js`). Run in the IDE uses this bundle, so engine changes don't show up until you rebuild.
- `demos/castle.b3d.json` and `standalone_demo/` (not committed; the Pages workflow builds it) (also from `js/cart.js`, `js/export.js` and anything in `demos/`).
- `docs/API.md` (from `js/apidocs.js`).
- **The IDE's offline files** `ide-sw.js` and `ide.webmanifest`. `ide-sw.js` lists every file the IDE uses and a fingerprint of their contents, so it changes whenever anything in `index.html`, `player.html`, `webgl-check.html`, `css/`, `js/`, `demos/`, `vendor/` or `runtime/` changes. That's how the installed IDE learns to re-download its offline copy. **Skip the build after an IDE-only change (a CSS tweak, a new demo, an Info tab edit) and installed IDEs won't keep the new files for offline use.** A brand-new top-level folder the IDE loads from must also be added to `SOURCES` in `tools/build-ide.mjs`.

The GitHub Action in `.github/workflows/runtime-bundle.yml` builds with Node 20, fails if any of these committed files differ from a fresh build (`docs/API.md` included), then installs Playwright's Chromium and runs `npm test`.

**Exported games** must stay fully standalone: the game is two files (`index.html` + `<slug>.js`), makes no network requests, and works from `file://`. Don't add CDN loads, ES modules (they fail from `file://`) or extra asset files the game needs.

**Installable IDE** (asked for by the owner, for offline desktop work): `tools/build-ide.mjs`, the last step of `npm run build`, writes `ide.webmanifest` (icons: the brand kit's `brand/web/icon-192.png` and `icon-512.png`, the cube tile, also listed as maskable since the cube sits well inside the safe zone) (`display: standalone`, a window on desktop; **scope is `./index.html` alone**, because `standalone_demo/` sits inside the IDE's folder and a folder scope would swallow the demo apps; **no `id`**, since an id is resolved from the site root, so the default, the full start URL, is used) and `ide-sw.js`. The service worker lists every file the IDE uses (`SOURCES`: folders, minus licenses, READMEs and demo PNGs, plus the few `brand/` files the IDE shows) and an FNV fingerprint of their paths and bytes, so any change makes a new `ide-sw.js` and the browser re-downloads the set. **Network first** (the owner's choice for the IDE, unlike the cache-first games): online every listed file is fetched with `cache: 'no-cache'` and the copy updated, offline the copy answers; anything not in the list (standalone demos, other sites) is left alone, so each demo keeps its own worker and stays installable. It fetches by URL, not by the request object (a navigation request can't be re-sent with options). `index.html` registers it on https or localhost, and at the bare folder address replaces the URL with `index.html` (so the page is inside the app's scope). The CI check also compares `ide-sw.js` and `ide.webmanifest`, so **rebuild after any IDE change** (the fingerprint covers `index.html`, `css/`, `js/`, `demos/`, `vendor/`, `runtime/`). A new demo or file in those folders is cached automatically; a new folder must be added to `SOURCES`. The installed IDE shares `localStorage` (autosave, save data) with the IDE in a tab.

**Installable app (PWA)** (agreed with the owner): exports and every standalone demo also get `manifest.webmanifest` (`display: fullscreen`, black colors, no orientation lock, by the owner's choice), `sw.js` and `icon-192.png`/`icon-512.png`, all made by `appFiles` in `js/export.js`. They're optional: `index.html` registers the service worker only on https (or localhost), so from disk or anywhere else they're ignored. A service worker can't be inlined (it must be its own same-origin file), which is why the zip grew from 2 files to 6. `sw.js` caches the six files on install and answers from that cache (cache-first); its cache name is `b3d-<scope>-<fingerprint of the game js, manifest and icons>`, so a new export installs as a new version the next time the game is opened online, and old caches of the same scope are deleted. Icons come from the cover (or the name card, `drawTitle` in `js/font.js`) scaled with nearest neighbour. `js/png.js` decodes the cover (DecompressionStream, in the browser and Node) and **encodes the icons with its own fixed-Huffman deflate**, not zlib, so the bytes are the same on any Node version: standalone exports come out the same on any machine (a Node 20 build was checked identical to a Node 22 one). The fullscreen button hides only when an installed app already fills the screen (`display-mode: fullscreen`, phones, or iOS `navigator.standalone`); on a computer an installed app opens in its own window (`display-mode: standalone`, desktop Chrome/Edge don't do `fullscreen`), so the button stays there. Desktop install works in Chrome and Edge (Windows, macOS, Linux, ChromeOS: the install icon in the address bar) and Safari 17+ on macOS (File > Add to Dock); Firefox only has an experimental "add to taskbar". Known limits: on itch.io and Game Jolt the game is in their iframe, so it can't be installed from there; on iPhone the installed app has its own `localStorage`, separate from Safari.

## Testing

**Run `npm test` before every commit** (CI runs it on every push too). It checks, in about a minute:

1. the map mesher's face counts on small maps whose answer is known, including the switch to 32-bit indices;
2. every demo in `demos/index.json` passes `b3d check`, and the cart the IDE's Save would write for it unpacks to a project folder and packs back byte for byte;
3. `b3d new` makes a game that passes `b3d check`;
4. every demo, and the `b3d new` game, runs headless for 300 frames with buttons held and tapped (and a click) without throwing. A failure names the demo and the line (`code:79: x is not defined`).

Part 4 needs Playwright's Chromium (`npx playwright install chromium`, once). Where that download isn't possible, set `B3D_CHROMIUM` to a Chrome or Chromium already installed (`B3D_CHROMIUM=/usr/bin/google-chrome npm test`); the `b3d` command's headless runs honor it too. `npm test -- --quick` skips part 4. The script is `tools/test.mjs`: when you add a demo it's tested automatically; when you add an engine feature, add a demo that uses it or a check to the script.

`npm test` only shows that nothing throws and the formats hold. Behaviour (physics, rendering, the IDE's editors) was checked by hand as each feature was added, with Playwright and headless Chromium (`--use-gl=swiftshader --enable-unsafe-swiftshader`, which supports WebGL 2) and the repo served with `python -m http.server`: **`docs/TESTING.md`** records what was checked and how, feature by feature. Check a changed feature the same way and add to that file.
